# SQLite: проверка хранения и восстановления

Проверен код ветки PR #53 после исправления диагностики конструктора Runtime
в коммите `911660e`. Реальная база VPS не получена и не изменялась.
Проверки используют отдельные временные SQLite-файлы; заполнение диска
моделируется лимитом страниц одной тестовой БД, не заполнением файловой системы.

В Capitalizator уже были WAL, synchronous=FULL, busy_timeout=10000,

с fsync/проверкой хеша. Переход на PostgreSQL или добавление ORM сам по себе
не исправляет приведённые ниже ошибки. Архитектура рассчитана на один VPS;
масштабирование писателей и требования к нагрузке здесь отдельно не измерялись.

## Воспроизведённые проблемы и исправления

| Проверка | До изменения | После |
| --- | --- | --- |
| SQLite реально возвращает SQLITE_FULL | Повторный ROLLBACK подменяет причину на «no transaction is active» | Проверяется in_transaction; сохраняется SQLITE_FULL, следующие записи возможны после отката |
| INSERT OR ROLLBACK нарушает уникальность | IntegrityError заменяется ошибкой повторного отката | Исходная IntegrityError сохраняется |
| Сбой посередине создания схемы | В тесте осталось 12 таблиц; соединение не закрыто явно | DDL и метаданные миграции в одной транзакции; при ошибке соединение закрывается |
| Неизвестная будущая схема | Нет проверки версии | Неподдерживаемый user_version отклоняется до изменения БД |
| Исчезнувшая БД при snapshot | sqlite3.connect создаёт пустой файл | URI mode=ro отказывает без создания файла |
| Завершение backup | Два соединения оставались открытыми при удержании ссылок | Оба явно закрыты до вычисления файловых хешей |
| Корректный Parquet с изменёнными данными | Можно получить новый файловый хеш повреждённой копии | Копия сверяется с хешем строк и count из сохранённого manifest; при несовпадении sha256.json не публикуется |

Дополнительно проверен отказ самого ROLLBACK: первоначальная ошибка сохраняется,
сбой отката добавляется в exception notes, непригодное соединение закрывается.
Схема версии 0 обновляется до версии 1 без пересоздания таблиц; повторное открытие
сохраняет данные. Версия относится к формату хранения, отдельно от policy модели.
Это начальная версия миграций, а не универсальный движок преобразования любых схем.

В startup-журнал и `/api/status.database` добавлены фактические SQLite version,
source_id, user_version, journal_mode, synchronous и busy_timeout. Они снимаются
при открытии Store; status не выполняет полный integrity_check на каждом запросе.

## Почему эти изменения нужны

SQLite документирует автоматический откат при некоторых ошибках, включая
SQLITE_FULL/IOERR. Проверять состояние транзакции перед повторным откатом
необходимо для сохранения исходной причины.
[SQLite transactions](https://www.sqlite.org/lang_transaction.html).

В Python контекст `with sqlite3.connect(...)` управляет транзакцией, но не
закрывает соединение. Теперь backup использует явное закрытие через closing.
DDL выполняется отдельными complete statements внутри общей транзакции,
поскольку executescript может предварительно закоммитить активную транзакцию.
[Python sqlite3](https://docs.python.org/3.12/library/sqlite3.html).

Для живой БД используется существующий SQLite Backup API, затем копируются и
проверяются архивы, на которые ссылается этот снимок. Копирование только основного
файла работающей WAL-базы не равно согласованной резервной копии.
[SQLite Backup API](https://www.sqlite.org/backup.html).

## Версия SQLite и пределы проверки

В тестовом окружении **SQLite 3.53.1**. В документации SQLite описана редкая
WAL-reset ошибка конкурентных операций: upstream-исправление есть в 3.51.3 и
позднее, также указаны backports 3.44.6 и 3.50.7. Наш тестовый движок содержит
это исправление. Версия и патчи SQLite внутри текущего контейнера VPS неизвестны;
версия Ubuntu или Python не доказывает версию связанной библиотеки.
[SQLite WAL-reset](https://www.sqlite.org/wal.html#walresetbug).

Короткая проверка текущего контейнера:

```bash
docker exec capitalizator-fusion-1 python -c 'import sqlite3; print(sqlite3.sqlite_version)'
```

В журнале релизов уже есть SQLite 3.53.4 с дополнительными исправлениями.
Тестовый движок 3.53.1 поэтому не объявляется последним или свободным от всех
известных ошибок. Для VPS следует проверить конкретную сборку/патчи поставщика.
[SQLite release history](https://www.sqlite.org/changes.html).

Новые тесты проверяют SIGKILL отдельного процесса посередине транзакции,
сохранение commit после повторного открытия, integrity_check, четырёх
конкурирующих писателей без потери обновлений, изоляцию читающего снимка,
восстановление backup и соответствие его файлов контрольным суммам.
SIGKILL процесса не моделирует отключение питания или отказ SSD.

Не проверены физическое состояние базы/диска VPS, отключение питания,
сетевые файловые системы, хранение резервной копии на другом хосте и восстановление
всего сервера. Тесты не дают гарантии «ошибок больше никогда не будет».
При обнаружении повреждения код сообщает ошибку и не удаляет/не «ремонтирует»
автоматически торговый журнал. Backup с отсутствующим sha256.json считается
незавершённым; после сбоя используется новый каталог назначения.
