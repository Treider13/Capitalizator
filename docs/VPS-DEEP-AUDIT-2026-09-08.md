## Дополнительно воспроизведённые дефекты

| Сценарий | До повторной проверки | Исправленное поведение |
| --- | --- | --- |
| Дочерний trainer остановлен SIGSTOP; задание 2 MB, timeout 0.3 s | Основной trainer зависает на отправке; через 5 s пришлось завершить тестовую группу процессов | TimeoutError с фазой send; завершение примерно за 0.92 s вместе с остановкой дочернего процесса |
| Получена только часть ответа Pipe | recv может ждать оставшиеся байты, хотя poll уже вернул готовность | Общий дедлайн включает send и полный recv; частичный ответ проверен отдельным процессом |
| Worker возвращает None до запроса остановки | Поток мёртв, failed=false, errors={} | Неожиданный выход регистрируется как ошибка с traceback |
| Worker завис до первого beat | Watchdog не знал о нём | Начальный heartbeat регистрируется при запуске |
| Maintenance завис | Watchdog находился внутри maintenance и сам не проверял состояние | Отдельный watchdog; health независимо вычисляет просроченные heartbeat |
| Worker восстановил heartbeat после stale | Его запрет worker_stale оставался | Снимается только соответствующий запрет; пауза и другие причины сохраняются |

Доказательства: [до](verification-2026-09-08/deep-fault-baseline.json),
[после](verification-2026-09-08/deep-fault-patched.json).
SIGSTOP и повреждённый ответ — искусственно введённые неисправности локального
стенда, не установленные события VPS. Исправлена возможность таких зависаний;
причинность именно для 12 прежних рестартов не доказана.

IPC теперь обслуживает один поток на одно задание. При прерывании дочерний
процесс останавливается, канал становится непригодным для повторного использования.
Закрытие не отправляет сообщения в потенциально заполненный pipe. В нормальном
простое закрытие родительского конца передаёт EOF для штатного завершения.
Завершение зависшего процесса ограничено по времени; дедлайн не является
гарантией real-time планирования ОС. Python отдельно предупреждает о повреждении
pipe после принудительного завершения его участника — поэтому переиспользование
запрещено. [Документация multiprocessing](https://docs.python.org/3.12/library/multiprocessing.html).

## Диагностика после следующего сбоя

Сохраняются необработанные исключения и первая причина аварийного запуска.
Добавлены периодические heartbeat/очереди раз в минуту и Python-стеки всех
потоков при переходе в watchdog_stale. Снимок делается до ожидания торгового
shared.lock, чтобы зависший владелец этого lock не скрыл место остановки.
Стек не включает значения локальных переменных; строки известных форматов
ключей и Authorization маскируются, в том числе во вложенных полях.

Watchdog не пытается принудительно убить Python-поток или разрешить торговлю
с устаревшими данными. Возобновление heartbeat снимает только его конкретный
запрет; рыночная свежесть, сверка счёта, пауза и прочие проверки остаются.
Если зависнут ОС, файловая система или сам watchdog, абсолютной гарантии записи
нет. `/api/health` возвращает 503 для просроченного heartbeat, если HTTP ещё
может отвечать. Неизвестные проблемы не объявляются исправленными.

В Compose включён `PYTHONFAULTHANDLER=1`. В отдельном Python-процессе
искусственный SIGABRT оставил fatal traceback в stderr (core dump отключён).
[Вывод](verification-2026-09-08/native-crash.json). Это не проверка Docker/OOM:
SIGKILL и авария хоста по-прежнему требуют внешних журналов.

## Почему модель/контуры могут работать, а сделок нет

По присланному status общий запрет был `paused=true`. Дополнительно SOL не имел
новостного покрытия, XAU требовал отсутствующий spot. Исправление XAU уже входит
в патч: только linear на резервировании, окончательной отправке и replay.

Важное различие из присланных ранее наблюдений: liquidation pressure в режиме
`observe` с `affects_orders=false` не запрещает торговлю. Поле `would_block`
показывает гипотетический результат наблюдателя. В Engine оно записывается в
журнал и не используется как разрешение/запрет реальной заявки. Обвинять этот
контур только из-за `would_block=[Buy,Sell]` было бы неверно.

`passed=false` — отказ Live-квалификации модели, а не самостоятельный запрет
Demo. При этом Demo всё равно требует положительного net edge, SMC-условий,
контракта/реакции, новостей, данных и риска. Ранее часть отказов описывалась
общим `entry_not_authorized`. Теперь эта запись содержит конкретные blockers:
paused, broker_not_ready, mode_switching, metadata/news и т. д. Дополнительно
записываются ожидание контекста и устаревший рынок, которые раньше могли
завершать обработку блока без объяснения.

Добавлена команда для телефона, только чтение:

```bash
docker exec capitalizator-fusion-1 python -m capitalizator.fusion.diagnose --userdir /data/fusion
```

`--pair SOLUSDT` сокращает вывод; `--json` даёт полный отчёт. Читаются status и
ограниченный фрагмент decisions через SQLite mode=ro. Не создаётся отсутствующая
БД, не запускается runtime, не отправляются заявки. Запрос ограничен 20 000
строками и временем исполнения. Отчёт различает текущие проверки книг/новостей
и частоты исторических записей разных этапов; эти частоты не являются
вероятностью сделки и не описывают всю историю или только текущий запуск.

## SOL: что подтверждено при более глубокой проверке

| Источник | Практическая роль | Ограничение |
| --- | --- | --- |
| [Solana Compass](https://solanacompass.com/tokenomics) | Бесплатная публичная информация о locked stake, будущих/прошлых разблокировках, эмиссии | Не подтверждены подходящий машинный endpoint, полнота и точность для нашего фильтра |
| [CryptoRank SOL](https://cryptorank.io/price/solana/vesting) / [API v3](https://docs.cryptorank.io/api-reference/vesting-%26-token-unlocks/upcoming-token-unlocks) | Кандидат на коммерческий API календаря | Endpoint требует ключ и Pro; полученная публичная страница SOL содержит несогласованную карточку другого тикера, использовать её как точное расписание нельзя |
| [DefiLlama SOL](https://defillama.com/unlocks/solana) | Контекст supply и staking rewards | В полученном разделе Unlock Events показаны staking rewards; в методике указаны прогнозы будущей эмиссии и отсутствие моделирования burns |
| [Messari SOL](https://solana.messari.io/token-unlocks) | Дополнительная страница для сверки | В доступном ответе только оболочка; календарные записи не получены |
| [CoinMarketCap Keyless](https://coinmarketcap.com/api/documentation/pro-api-reference/keyless-public-api) | Бесплатные рыночные данные для некоторых задач | В проверенном перечне не подтверждён нужный календарь unlocks; наличие пункта сайта не доказывает API-доступ |

Solana Compass отдельно различает lockup и cooldown при unstaking; совпадение
снятия блокировки с немедленной продажей не гарантируется. Разметка владельцев
частично эвристическая, что автор прямо раскрывает. Для автономного фильтра
важны source/known_at, точность, полнота страниц, stale и изменения календаря.

Вывод: бесплатный **информационный** аналог найден — Solana Compass.
Автоматически надёжная замена Tokenomist ещё не аттестована. DefiLlama API plan
платный; показанные staking projections не являются доказательством точного
cliff-события. Снятие SOL coverage без проверенного источника было бы подменой
отсутствующих данных, поэтому не сделано.

## Практики активных проектов 2026 и работа с моделью

Проверены Freqtrade/FreqAI, Hummingbot и NautilusTrader как инженерные ориентиры.
Их звёзды и релизы не являются независимым рейтингом доходности.

- [FreqAI](https://www.freqtrade.io/en/stable/freqai-running/): сохранять результаты
  реальных прогнозов и сравнивать их с backtest; отделять обновление/возраст модели
  от готовности исполнения. У нас возраст уже ограничен, добавлены диагностика
  входов и отдельный хронологический model_audit.
- [Hummingbot #8437, 26.08.2026](https://github.com/hummingbot/hummingbot/issues/8437):
  пользователь сообщает о потоке повторяющихся ошибок конвертации комиссии и
  нагрузке на CPU/журналы. Это сообщение автора issue, не воспроизведённый здесь
  дефект Hummingbot. Практический вывод: логировать переходы состояния и ограничивать
  повторы. Наш watchdog сохраняет стек один раз при переходе в stale, затем recovery.
- [Hummingbot #8413, 07.08.2026](https://github.com/hummingbot/hummingbot/issues/8413):
  сообщение о неверном масштабе funding в отображении. Вывод для исследований:
  проверять единицы, интервалы funding и net из реальных исполнений, а не доверять
  красивому числу процентов. В этой работе ошибка funding Capitalizator не установлена.
- [NautilusTrader](https://nautilustrader.io/docs/latest/concepts/reconciliation/):
  восстановление состояния через журнал и сверку с площадкой. Существующие
  executor/reconciliation и запрет при неполной истории сохранены.

У модели уже исправлено расхождение между validation и реальным worst-expert
edge. Дальнейшее увеличение сложности без VPS-данных сейчас необоснованно.
Конкретные гипотезы для проверки на записанной истории:

1. Разделить метрики по символам, фактическому горизонту и рыночным режимам:
   8192 rows не равны 24 часам независимой истории.
2. Сравнить предсказуемое движение с полными издержками. В присланном отчёте
   RMS метки около 5.36 bps, дефолтные maker+taker уже 7.5 bps без spread.
3. На одинаковых событиях сравнить A/B/C/D и простые baseline. Считать отказы
   по этапам; не отключать фильтры только ради появления сделок.
4. Сохранить внешние хронологические holdout/forward участки и все испытанные
   варианты, включая неудачные. Множественный подбор завышает видимые результаты;
   это разбирается в [Deflated Sharpe Ratio](https://www.davidhbailey.com/dhbpapers/deflated-sharpe.pdf).
5. Оценивать исполненные net returns, drawdown, неизвестные заявки/позиции,
   комиссии/funding/slippage и стабильность. Label proxy не переводить в обещания
   процентов счёта. Синтетический поток не использовать для выбора прибыльной модели.
