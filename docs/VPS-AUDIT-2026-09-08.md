Изменения основаны на `c123e32f54a8c7e04301477df9758dfc8e82f90f`.
Исходный код установлен локально на Linux / Python 3.12.13 с exact constraints
`requirements.lock`, включая `[dev,live,hyexec,talib]`: 42 совместимых пакета.
Это исправление конкретных дефектов, не сертификат отсутствия всех ошибок.
Доступа SSH к VPS, его базы и полного биржевого журнала в этой проверке не было.

разрешений (`network approval was cancelled before a decision was returned`);
ограничение не обходилось. Контейнерная сборка и реальная торговля не проверены.

## Перезапуски: воспроизведённый дефект

В исходном Supervisor исключение сохранялось только в памяти, ставился failed,
основной цикл завершался с exit=0. `restart: unless-stopped` допускает новый
запуск и после такого завершения. Поэтому сообщение startup могло быть почти
единственным следом. Ошибки WebSocket рядом по времени не доказывают причинность.

В отдельный процесс CLI внедрено исключение worker. При неизменном сценарии:

| Версия | Код выхода | stderr | Сохранённая причина |
| --- | --- | --- | --- |
| Исходная | 0 | Пустой | Нет |
| Исправленная | 1 | Имя worker и полный traceback | Есть; читается новым Runtime |

Исходные выводы: [до](verification-2026-09-08/fault-baseline.json),
[после](verification-2026-09-08/fault-patched.json).
Сценарий воспроизводится тестом
`test_real_cli_worker_failure_exits_nonzero_and_survives_restart`.
Это доказательство потери диагностики, **не определение конкретного worker,
упавшего на VPS**. Для окончательного расследования нужен следующий реальный
incident log либо старые внешние журналы хоста.

Добавлены JSONL с ротацией, run_id, startup/shutdown, сигнал завершения,
причина паузы, атомарный last_failure.json и код выхода 1 при сбое worker.
Ошибки очистки не перезаписывают первую аварию. SystemExit в worker тоже
регистрируется. Ошибка привязки HTTP-порта записывается как main_failure.
stderr сохраняет исходное исключение даже при невозможности записи в каталог.
Маскируются известные формы ключей и Authorization; locals не записываются.
SIGKILL/нативный crash/OOM могут потребовать stderr, Docker и journald: полный
Python traceback в этих случаях не гарантирован.

`/api/health` проверяет ошибки, живые потоки и уже выявленные watchdog-зависания.
Это не аттестация рыночных данных или готовности торговли. Compose использует
этот endpoint; unhealthy само по себе не перезапускает контейнер.

## Золото: только фьючерсы

Исключение ограничено точным символом `XAUUSDT`. Его spot worker не запускается,
консоль показывает `not_required`. Резервирование, финальная авторизация и replay
используют linear. Сохранены проверки времени receipt/exchange/monotonic,
поколений фьючерсного потока, спреда, направления давления, новостей, дневных
уровней, контракта, состояния счёта и риска. BTC/ETH/SOL/BNB/DOGE по-прежнему
требуют обе книги. PAXG/XAUT не используются как замена.

Проверено тестами: XAU допускает резервирование и финальную авторизацию без spot;
BTC не допускает; устаревшая linear-книга и пауза запрещают отправку XAU.
Это проверка разрешения, не подтверждение исполнения конкретного инструмента
на Bybit в момент аудита.

Источники: [CryptoRank endpoint](https://docs.cryptorank.io/api-reference/vesting-%26-token-unlocks/upcoming-token-unlocks),
[DefiLlama планы](https://docs.llama.fi/pro-api), [Solana staking](https://solana.com/staking).
Это кандидаты, не уже проверенные замены. Платные подписки не приобретались,
адаптер с вымышленными ответами не добавлялся. Само наличие Unix timestamp в
схеме API не доказывает точность времени события до секунды.

Текущий Tokenomist adapter намеренно не принимает AI/неточные даты как точные
минутные окна блокировки. Для замены нужна реальная выборка SOL, включая пустой
успешный ответ, пагинацию, 401/403/429, stale, перенос/отмену события и known_at.
Без этого снятие `coverage=false` создало бы ложное подтверждение данных.
Каталог public-apis не предоставляет таких гарантий и не отменяет тарифы.

## Почему наличие модели ещё не создаёт сделку

Последовательность фактического допуска включает свежие данные/модель,
sweep, согласование HTF/LTF, retracement, положительный net edge,
дневные уровни и net RR, подтверждение реакции, затем новости/счёт/риск
и повторную проверку перед отправкой. Отдельная модель не заменяет эти условия.
Для диагностики на реальном архиве нужно считать причины отказа каждого этапа
и сравнивать существующие варианты A/B/C/D при одних событиях и издержках.
Такого архива в окружении нет: причинную долю каждого фильтра не измеряли.

Обнаружено расхождение Atlas: test-net использовал смесь экспертов, а реальный
вход — минимум условных оценок за вычетом ошибки оценки и издержек. Исправлена
валидация, чтобы считать сигналы по тому же Forecast.edge. Это не ослабление
входных условий и не доказанное улучшение P&L. В отчёт добавлены signal_count,
abstentions, издержки/предсказание в bps, длина истории/горизонт и причины отказа.
Bootstrap теперь пересэмплирует соседние временные группы блоками; выбранная
длина блока эвристическая, независимость и условное покрытие не гарантированы.

Присланный test MSE лучше нулевого прогноза примерно на 0.0162%. RMS метки
около 5.36 bps, тогда как дефолтная пара maker+taker комиссий даёт 7.5 bps
ещё до spread. Это основание проверить горизонт и издержки; из этих агрегатов
нельзя заключить, что ни один будущий вход не может быть прибыльным.

Добавлен `model_audit`: expanding chronological folds, обучение только на
созревших до начала holdout метках. Тест изменения будущих меток подтверждает,
что ранний fold от них не меняется. Вывод — label proxy, не счётная доходность:
перекрывающиеся метки нельзя суммировать как прибыль. Для исследования модели
сначала нужны несколько рыночных режимов, затем отдельный внешний holdout,
издержки/филлы и сравнение с простыми baseline. Размер модели без этих данных
увеличивать необоснованно.

Политика изменена на `fusion-11-xau-linear-model-gates`: старые модели и
Live-квалификация не применяются автоматически, сохраняется операторская пауза.
Новая модель переобучается на новых samples политики.

## Что необходимо для завершения проверки реального сервера

1. Применить проверенную ветку на VPS с сохранением userdir, владельца тома,
   существующей конфигурации и паузы. Сервер в этой сессии не обновлялся.
2. После реального сбоя прочитать `logs/last_failure.json` и сопоставить run_id,
   Docker exit/signal, OOM/journald. Без этого конкретный инициатор 12 рестартов
   остаётся неизвестен, а не автоматически считается исправленным.
3. Получить backup без secrets и записанные события/specs/новости VPS. Запустить
   `model_audit` и полный A/B/C/D replay в отдельный output, затем Demo forward.
   Сравнивать net после комиссий/funding/slippage, drawdown и число исполнений,
   стабильность по времени/символам. Не оптимизировать и не оценивать на одном
   и том же holdout. Нулевые сделки не подтверждают исполнение контура.
4. Выбрать и проверить источник SOL реальным авторизованным ответом. До этого
   SOL остаётся без полного допуска новостей, даже после исправления runtime.

Короткая команда после обновления, без ручного копирования большого status:

```bash
docker exec capitalizator-fusion-1 cat /data/fusion/logs/last_failure.json
```

Если файл ещё отсутствует, это означает отсутствие сохранённой Python-ошибки,
а не доказательство идеальной работы. Нельзя честно гарантировать «топ-1 мира»
по процентам, будущую прибыль или 100% безошибочность по этому прогону.
